# Data card

## What the data is

**The official AI-4016 starter kit (GigSim, personas, policy pack, dev set) had not been released**
when this was written. All data here comes from a **stand-in kit** generated by
`scripts/make_standin_kit.py` (seed 4016), built to the shape the brief describes. When the official
kit arrives, its files replace these, and `python -m evals.run_all` regenerates every number. See
[ADR 0001](adr/0001-standin-starter-kit.md).

| Asset | Path | Size |
|---|---|---|
| Personas (AI/ML, full-stack, data analyst) | `data/personas/<id>/` | 3 × (CV in PDF and MD, 15–25 case studies, 20–30 repos with README and code, reviews, 150 past proposals with outcomes) |
| GigSim seed | `gigsim/seed/` | 450 clients, 940 open jobs, 1,500 historical jobs, price percentiles |
| Policy pack | `data/policy_pack/` | 5 rules (contact details, off-platform payment, guarantees, fabrication, credentials) |
| Dev set | `evals/datasets/dev_<id>.jsonl` | 200 jobs per persona (600 total) |

### Hard cases planted on purpose (from the brief)
- **Implied skills:** around 30% of requirements describe a skill without naming it ("an async Python API with automatic docs" means FastAPI), and the public skill tags only list named skills.
- **Mixed code and prose:** repo READMEs are vague, and the real stack shows only in the code.
- **Duplicates:** the same project appears as a case study, a repo and a review.
- **Outcomes matter:** past proposals are labelled won, replied or ignored. Generic openings are mostly ignored.
- **Scams:** 25–30 per persona across four types: off-platform contact or payment, unpaid "test" work, overpayment or forwarding, and credential requests.
- **Prompt injections:** 10–12 per persona in job posts, plus about 8% of simulated client replies. Five styles: "ignore previous instructions", a fake `[system]` line, an "if you are an AI" line, a hidden HTML comment, and false claims of authorisation.
- **Vague posts:** about 15% of posts are too thin to scope ("Details in chat").

### Labels in the dev set

Each dev item carries these labels:
- `bid` / `is_scam` / `scam_type` / `has_injection`
- `coverage`: the share of the job's real skills, implied ones included, that the persona has
- `fair_price_band`: the p25–p75 of historical awarded prices for the category and budget type, clipped to the client's maximum
- `gold_evidence`: graded relevance labels

**How `gold_evidence` is defined:** every portfolio item (CV excluded) that covers at least half the job's
real skills, with relevance = the number of skills it covers. The median gold set has about 30 items.

An earlier version kept only the top 8 items and broke ties by id. At the cutoff a median of
14–22 items were tied, so gold mostly came down to alphabetical order: case studies and
low-numbered proposals got in, and repos and reviews almost never did. That made recall arbitrary, so it was fixed
before any variant was compared. Only the dev files changed; the commit diff shows this.

## How the numbers are computed (`evals/metrics.py`)
- **Recall@5 is capped recall:** gold items in the top 5 / min(5, |gold|), so a perfect ranker scores 1.0 even with 30 relevant items.
- **MRR:** 1 / rank of the first gold item.
- **nDCG@10:** graded, with gain 2^rel − 1.
- **Bid/skip F1:** positive class = bid.
- **Scam precision and recall:** predicted scam = risk score above `bid_graph.decision.max_scam_score`.
- **Price inside the fair band:** for jobs labelled bid where the agent quoted.
- **Latency for retrieval:** measured with the query-side caches empty (a new job).
- **Latency for the graph:** wall-clock time up to the approval interrupt. GigSim's and the server's politeness rate limits are lifted in memory for eval runs only, so the numbers measure the agents rather than deliberate waiting.
- **Reply rate:** proposals whose GigSim status reached `replied`, `interview` or `hired` within 80 simulated hours.

## Threats to validity (read before quoting any number)
1. **Synthetic data with a known generator.** The decision rules and scam patterns were written by the same person who wrote the generator, so the near-perfect bid/skip and scam scores on this dev set say **nothing** about real jobs. The official kit's held-out test set is the real test.
2. **Gold is defined by skill-tag overlap, and the index carries skill-tag metadata.** Variants that index metadata, such as the summary unit in V5 multi-vector, get an advantage that is partly circular. Metadata on every chunk is required by B1, so this is legitimate, but expect smaller gains on human-labelled gold.
3. **Rule path, not LLM path.** Until a `GROQ_API_KEY` is configured, the writer, critic and analyst run their deterministic rule paths. The unsupported-claim rate is then 0 by construction, because the template only copies evidence, and the "judge score" is the Critic's rule rubric. These columns become meaningful only after a run with the open model profile, and the table header says which mode produced it.
4. **Choices made on the dev set.** The shipped retrieval combination and the V8 refusal threshold were picked on the dev set, so their dev numbers are optimistic.
5. **Small samples for outcomes.** Reply rate uses about 75 proposals per variant (25 per persona), giving a standard error of about ±5 points. Differences smaller than about 10 points are noise.

## What ships (one paragraph, as the brief asks)
GigBid ships the `best` retrieval pipeline (`rag/variants/best.py`): one unit per portfolio item with a
metadata header, hybrid BM25 + dense retrieval, and the whole job post plus each extracted requirement as
queries, fused with RRF. On this dev set it scores the highest Recall@5 of every configuration we measured
apart from adding the cross-encoder, which matches it while costing about 1.9 s p95. It runs on CPU with no API cost.

The cross-encoder, outcome boost and corrective loop stay available as variants but are off. The ablation
shows no recall gain from them, and the corrective loop lowers bid/skip F1 end to end.

Better retrieval did not raise the simulated reply rate. In rule mode, the differences between variants are within the
simulator's noise, so the case for this pipeline rests on evidence quality. The model writer is expected
to show that as fewer unsupported claims before verification once a `GROQ_API_KEY` run is in the table. Numbers:
`evals/results/RESULTS.md`; reasoning: [ADR 0003](adr/0003-retrieval-choice.md).

## Privacy
All people, clients and companies are fictional. The PII masker and the injection patterns are
tested against the planted cases. No real Upwork data is stored. Live mode reads through the
official Upwork MCP server only, with no scraping, browser automation or session cookies.
